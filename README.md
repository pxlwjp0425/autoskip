# 快跳 AutoSkip

一个基于 Android **无障碍服务（AccessibilityService）** 的自动跳过工具 —— 和「李跳跳」同一类东西：  
界面上一出现「跳过 / 关闭」这类按钮，它替你点掉。

规则不写死在安装包里，而是走 **订阅地址**：改规则不用重新装 APK，随时点一下「更新全部规则」就生效。

---

## 一、它到底怎么工作

```
开屏广告弹出
   ↓  系统回调无障碍事件
无障碍服务收到窗口事件（onAccessibilityEvent）
   ↓
抓取当前界面的节点树
   ↓  用规则里的关键词 / 控件 ID / 正则去匹配
命中「跳过」按钮
   ↓  performAction(ACTION_CLICK)，不行就用手势点坐标
广告关闭，直达首页
```

三点值得强调：

1. **全程本地**。匹配在手机上完成，不上传任何界面内容，App 也没有收集数据的代码。
2. **只动命中的东西**。没命中规则的按钮，它一个都不会碰。
3. **有防误触**。每条规则有 `maxClick`（单屏最多点几次）和 `cooldown`（冷却时间）。
4. **绝不点到自己**。扫描前强制校验「事件来源的应用 == 真正拿到焦点的窗口」，     
   点击前再复核一次。不做这层校验的话，「跳过」这种通用词会把快跳自己界面上     
   「启用自动跳过」那个开关当成广告按钮点掉 —— v1.2.3 修的就是这个。
5. **绝不点大片区域**。命中节点占屏面积超过 40% 就判定为列表/页面容器，直接放弃。     
   真正的关闭/跳过按钮都是小控件；反过来，被点中的如果是信息流列表这类整屏容器，     
   点它的正中心就会落到里面的某条内容上 —— 用户看到的就是「一进页面就自己乱跳转」。     
   同一条护栏也用在「向上找可点祖先」上：祖先太大就不点它，退回点节点自身中心。
6. **可以按应用关掉**（v1.5.0）。不想让快跳碰某个 App，在「应用」页关掉它就行 ——     
   规则和自动识别一起停，而且闸门在读节点树**之前**，不产生任何开销。
7. **可以按规则组关掉**（v1.7.0）。比整应用摘出去细一档：淘宝的开屏广告别管、更新提示照跳。     
   两级粒度 —— 只在某个应用里关（`包名#组名`），或者对所有应用都关（`*#组名`，在「规则」页的全局卡里）。
8. **规则库里没有的 App 也能试**（v1.5.0，实验性）。靠按钮的形状（含跳过词 + 小 + 在角上 + 短）     
   认出开屏跳过，再套用和规则命中完全相同的安全闸门。默认开启，可随时关掉。
9. **界面是底部导航四页**（v1.7.0）：首页 / 应用 / 规则 / 设置。原来八块内容堆在一页上，     
   首屏要滚八屏；现在一页一类，关停的东西用角标提醒（`应用 3`）。

## 三、编译

### 方式一：命令行

```bash
# 本机已有的工具链
export JAVA_HOME=/d/dev/jdk-21.0.12.1+1
export ANDROID_HOME=/d/Android/Sdk
export GRADLE_USER_HOME=/d/dev/gradle-home

/d/dev/gradle-8.14.3/bin/gradle -p /path/to/autoskip assembleRelease
```

Windows 上双击 `build.bat` 也行（脚本里已经填好本机路径）。

产物：`app/build/outputs/apk/release/app-release.apk`

### 方式二：Android Studio

直接 `File → Open` 打开 `autoskip` 目录，等 Gradle Sync 完成后：  
`Build → Build Bundle(s) / APK(s) → Build APK(s)`。

> 工程用了 `local.properties` 指定 SDK 路径。换机器时改这一行：>   
> `sdk.dir=D:/Android/Sdk`

### 签名

`keystore/autoskip.jks` 是自签名证书（口令 `autoskip123`，别名 `autoskip`）。  
仅自用足够；要发布请换成你自己的证书。若删掉这个文件，构建仍能通过（会退化成未签名）。

## 四、安装与授权

1. 安装 APK（首次需允许「安装未知来源应用」）。
2. 打开 App → 点「去开启无障碍权限」。
3. 在系统无障碍列表里找到 **快跳** → 打开开关 → 确认。
4. 回到 App，顶部应显示绿色的「已开启」。

**国产 ROM 必做**（否则服务会被系统杀掉）—— 具体做法见**第五节**，App 里有按钮直达：

| 系统                 | 要做的事                      |
| ------------------ | ------------------------- |
| MIUI / 澎湃          | 省电策略 → **无限制**；允许自启动；后台锁定 |
| EMUI / HarmonyOS   | 应用启动管理 → 手动管理 → 全部打开      |
| ColorOS / OriginOS | 允许后台运行 + 自启动              |
| 原生 / 类原生           | 电池优化 → 不优化                |

### ⚠️ 开关是灰色的、点不动（Android 13+ 的「受限制的设置」）

从 Android 13 起，**非应用商店安装（侧载）的应用默认拿不到无障碍权限**，系统会弹  
「未知来源应用，系统已拒绝此应用获取敏感权限」。小米澎湃、OPPO ColorOS、vivo OriginOS 都继承了这套策略 ——  
**这跟 App 本身无关，是系统在拦，任何侧载 App 都一样**。

解法只有四步，第 1 步是关键（多数教程会漏掉）：

1. **先点一次那个灰色的开关**，看到「已拒绝」弹窗后关掉它。     
   系统必须先记录「这个应用尝试申请过」，才会把解锁入口放出来。
2. 进 **设置 → 应用设置 → 应用管理 → 快跳**（App 内点「打开应用详情页」可直接跳到这一页）。
3. 点页面**右上角 ⋮（三个点）→「允许受限制的设置」**，再用指纹/密码确认。
4. 回到无障碍列表，「快跳」的开关就能正常打开了。

> 部分机型把「允许受限制的设置」直接平铺在应用详情页上，不用进 ⋮ 菜单。>   
> 另外，**用 adb install 装的应用有时不会出现这个入口** —— 这时请卸载后重新从「文件管理」里点 APK 安装一次。

**如果满页找不到 ⋮ 菜单，用电脑 ADB 强制开启**（最稳，任何 ROM 限制都绕得过）：

```bash
adb shell settings put secure enabled_accessibility_services com.laopeng.autoskip/com.laopeng.autoskip.SkipService
adb shell settings put secure accessibility_enabled 1
```

App 里点「复制 ADB 命令」可以一键复制这两条。

> ⚠️ 第一条命令会**覆盖**当前的无障碍服务列表。若手机里还开着别的无障碍服务>   
> （TalkBack、GKD、屏幕朗读等），必须先读出来再拼，否则它们会被关掉：
>
> ```bash
> adb shell settings get secure enabled_accessibility_services
> # 把输出和 com.laopeng.autoskip/com.laopeng.autoskip.SkipService 用英文冒号 : 连起来，再 put 回去
> ```

## 五、后台保活（免 root）

跳广告类 App 最常见的故障不是"规则不对"，而是**被系统悄悄清理掉了**。快跳用三重手段把它按住，全部不需要 root。

### 1. 前台常驻（核心，默认开启）

无障碍服务在 `onServiceConnected()` 里自己调 `startForeground()`，把整个进程提到**前台服务**优先级。系统内存回收时前台服务排在最后，国产 ROM 的"一键清理"也基本带不走它。代价是多一条常驻通知 —— 通知上会显示今日跳过次数，点击直接进设置。

> Android 14 起前台服务必须声明类型。快跳用的是 `specialUse`，并在清单里用>   
> `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 写明了用途，否则 `startForeground` 会直接抛>   
> `MissingForegroundServiceTypeException`。

### 2. 电池优化白名单（这一步比看起来重要）

进了白名单，系统不再冻结快跳，Doze 模式下也能正常响应界面事件。App 内一键跳系统弹窗。

**它还有第二个作用，而且是刚需**：Android 12 起禁止应用在后台启动前台服务，一旦触发就抛  
`ForegroundServiceStartNotAllowedException`。官方豁免清单里有一条正是「**用户关闭了该应用的电池优化**」。  
也就是说 —— 开机后无障碍服务被系统拉起时，App 进程还在后台，**只有进了白名单，那次 `startForeground()` 才会成功**。  
没进白名单的话，得等你手动打开一次快跳界面才能补上。

所以顺序建议：**先加白名单，再谈其它**。

### 3. 自启动 / 省电策略

各家 ROM 的入口都不一样，快跳内置了一份厂商页面清单，按顺序尝试打开，第一个能开的就用：

| 厂商           | 打开的页面                           |
| ------------ | ------------------------------- |
| 小米 / 澎湃      | 应用权限编辑（自启动 + 后台弹出界面同页）→ 备选省电策略页 |
| 华为 / 荣耀      | 应用启动管理                          |
| OPPO / 一加    | 自启动管理                           |
| vivo / iQOO  | 自启动管理                           |
| 魅族 / 三星 / 联想 | 各自的安全中心页                        |
| 其它           | 退回到应用详情页，手动找                    |

打开后把快跳的自启动打开、省电策略设为 **无限制**。

### 还能再做一步（只能手动）

在**最近任务列表**里给快跳加锁（下拉卡片 → 点小锁图标）。这样"一键清理"时它不会被一起带走。这一步系统没提供接口，只能手动点。

### 界面会告诉你现在到底稳不稳

保活区块的状态文字是实时体检结果，按严重程度排：

| 显示          | 含义                                    |
| ----------- | ------------------------------------- |
| 权限已开，但服务没在跑 | **最严重** —— 服务被杀了。去无障碍列表把快跳关一下再开一下即可恢复 |
| 电池优化：未豁免    | 系统可能随时冻结快跳                            |
| 已进入前台常驻 ✓   | 一切正常，常驻通知生效中                          |

### 保活的极限在哪

上面这些是"降低概率"，不是"绝对不被杀"。**真正的 100% 抗杀只有 root 一条路** —— 把 App 装成系统应用、写 `service.d` 开机脚本。代价大（解锁 Bootloader、刷内核、一步错就得重刷），而且 root 之后来路不明 APK 的危害会放大一个量级。日常使用，这三重保活已经够。

> 另外，`startForeground()` 在后台可能被拒这一条，快跳有兜底：**每次打开 App 界面时会检查一次**>   
> —— 如果服务已连上但没进前台，趁 App 在前台再补一次。

## 六、root 增强（可选）

免 root 那条路在第五节就走到头了 —— 电池白名单对应的是系统待机豁免里最高的一档（`standby bucket = EXEMPTED`），再往上没有档位可调。要继续往上只有 root。

快跳把 root 用在这四件事上（KernelSU / Magisk 通用，走 `/system/bin/su`）：

| 能力           | 做法                                                | 效果                                |
| ------------ | ------------------------------------------------- | --------------------------------- |
| **锁内存**      | `oom_score_adj = -1000`                           | 内存回收基本轮不到它                        |
| **免手动解受限设置** | `appops set ... ACCESS_RESTRICTED_SETTINGS allow` | 重装、清数据后不必再去点右上角 ⋮                 |
| **无障碍开关自愈**  | 守护脚本盯着开关记录，被清就补回                                  | HyperOS 上 `am force-stop` 会连它一起清掉 |
| **开机守护**     | KernelSU 模块 `autoskip_guard`                      | 重启后自动重做上面这些，并长期巡检                 |

### 它是怎么挂到系统里的

```
/data/adb/modules/autoskip_guard/          # App 装入的就是下面三个文件
├── module.prop          # 模块元信息，KernelSU 管理器据此识别
├── service.sh           # 开机 late_start 执行一次，等系统起来后把 guard.sh 挂后台
└── bin/guard.sh         # 真正干活的长驻循环（每 20 秒一轮）
```

> **守护模块已独立成仓库** → [pxlwjp0425/autoskip_guard](https://github.com/pxlwjp0425/autoskip_guard)。
> 同一份内容的发布口，额外带 `uninstall.sh`、打包脚本，以及完整的安装 / 验证 / 卸载说明；
> 也可以从那里下 zip 手动刷入（不装 App 单独用）。
> ⚠️ 这三个文件同时内嵌在 App 里（`GuardModule.java` 的三个文本块），
> **改脚本要两边同步，以 App 侧模板为准**。

`guard.sh` 的核心原则是**只在真的坏了的时候才动手**。因为 `settings put` 会让系统重新绑定无障碍服务（有几百毫秒闪断），正常状态下反复写反而更不稳定。所以每轮只做四件事：

1. 开关记录里没有自己 → 补回（**追加式**，不动机器上别的无障碍服务）
2. 进程不在 → `am start-foreground-service` 静默拉起（不弹界面）
3. `Bound services` 里没有自己 → 先把自己从开关列表摘掉再写回，逼系统走一遍重连
4. `oom_score_adj` 掉了 → 重新锁上

日志在 `/data/adb/autoskip_guard.log`，超过 300 行自动截断。模块目录被删掉（= 用户在 App 里关了开关）时，脚本下一轮会发现并自己退出。

### 为什么专门加了个空的 GuardService

无障碍服务是**系统绑定**的，没法用 `am` 直接启动。进程被系统彻底清掉后，只剩「启动 Activity」能重建进程 —— 那会直接把界面糊到用户脸上。

所以工程里多挂了一个空壳前台服务（`GuardService`），守护脚本拉起它就行：进程起来了，用户什么都看不见。它复用保活那条通知（同一个 id），不会多出一条。

### 实测：被强杀后 15 秒自动复活

```
$ am force-stop com.laopeng.autoskip
  3 秒后 pid: （空）
  3 秒后 无障碍: null                  ← force-stop 连开关记录一起清了
  t+15s  pid=[31089]  无障碍=[com.laopeng.autoskip/...SkipService]

### ⚠️ 首次必须手动授权一次（国产 ROM 的坑）

KernelSU 收到 App 的 su 请求时会弹授权窗，而**澎湃 / ColorOS / OriginOS 会把这个弹窗拦掉**。表现就是：点了「启用 root 增强」，只闪一句「没拿到 root 权限」，开关又弹回去 —— 而且它连弹窗失败的提示都不给。

App 里会直接弹引导框，也可以随时点「打开 KernelSU 授权页」：

1. 打开 KernelSU 管理器
2. 底部切到「超级用户」，在列表里找到「快跳」
3. 设为允许 ROOT
4. 回到快跳，再打开一次开关


**只做这一次。** 授权之后 `/data/adb/ksu/.allowlist` 里就有了记录，以后直接可用。

> 顺带：给 KernelSU 管理器自身的 appop `10021`（MIUI「后台弹出界面」）设成 allow 也有帮助，>   
> 但不是充分条件 —— 手动授权一次最省事。
>
> ```bash
> adb shell cmd appops set me.weishu.kernelsu 10021 allow
> ```

### 怎么关掉

关掉「启用 root 增强」开关会：移除 `/data/adb/modules/autoskip_guard/`（守护脚本下一轮发现目录没了会自己退出）、把 `oom_score_adj` 写回 100。

`ACCESS_RESTRICTED_SETTINGS` 和电池白名单不会撤销 —— 它们只是权限，留着没坏处。

## 七、从 GKD 订阅转换规则（仓库只带工具，不带规则数据）

GKD 有 9000+ 应用的活跃规则库，比从零手写高效得多。工程里带了完整的转换器链：

```bash
pip install json5

# 拉一份干净的上游订阅（这些地址已停止维护，但文件仍可取）
curl -sL -o rules/_src/AIsouler_gkd.json5 \
  https://registry.npmmirror.com/@aisouler/gkd_subscription/latest/files/dist/AIsouler_gkd.json5

# 转换成快跳规则格式
python tools/gkd2skip.py rules/_src/AIsouler_gkd.json5 rules/gkd-compat.json
```

产物 `rules/gkd-compat.json` 可以直接当作快跳的订阅地址用。**完整说明见 `rules/README.md`。**

> ### ⚠️ 规则数据不随本仓库分发
>
> `rules/gkd-compat.json` 和 `rules/_src/` 都在 `.gitignore` 里，clone 下来是空的，需要你自己生成。
> 原因：上游订阅大多**没有开源许可证**（= 保留所有权利），个别还明确声明**禁止传播**，
> 由它们派生的规则文件不能随本仓库再分发。
>
> **转换脚本（`tools/*.py`）是本项目原创代码，不受此限，照常分发。**
> 授权明细见 `rules/README.md` 的「授权说明」，或本文档第十三节。

实测（干净源，AIsouler + Adpro）：

| 指标                   | 数值                |
| -------------------- | ----------------- |
| 可转换                  | **61.3%**         |
| 输出                   | 1888 条，覆盖 721 个应用 |
| 带界面限定（`activityIds`） | 88.9%             |
| 误触实测（65 个常见 UI 文本）   | 常规按钮 **0 命中**     |

> 旧版本这里写的是「可转换 19%」，那是个**假数字** —— 合并脚本把 `rules` 的字符串简写>   
> 当列表遍历，把 `matches` 逐字符拆开，分母因此膨胀到 11585。真实成功率一直是 61%。

**剩下那 39% 转不了是正常的，也是刻意的。** GKD 的选择器支持层级（`A > B`）、  
索引、兄弟节点、宽高断言，快跳只有「文本 / 描述 / 资源 ID」三个维度。  
转不了的规则长这样：

```js
ViewFactoryHolder FrameLayout[childCount=5] > FrameLayout[childCount=1]
  > ImageView[childCount=0][id=null][desc=null][width<60 && height<60]
```

没有任何文字或控件 ID，硬转等于"点这个位置的图"，是灾难性的误触源 —— 所以全部丢弃。  
**留下的这些恰好是 GKD 规则里最耐改版的那部分。**

转换器做了这些防误触处理：精确匹配完整复刻（`text="跳过"` → 正则 `^跳过$`）、  
系统通用 ID（`android:id/content`）拉黑、短 ID 锚定到资源名末尾（`/arg$`）、  
泛词（"关闭""取消"）必须带 `activityIds` 才保留、无界面限定的规则单屏只点一次。

### 转换时最大的坑：把「上下文约束」当成点击目标

GKD 选择器形如 `A > B <<n C`，**只有 `@` 标记的那段才是点击目标**，其余段落都是  
定位用的上下文（祖先 `<` / `<<`、兄弟 `+` / `-`、后代 `>` / 空格）。

早期版本拿整串做关键词抽取，于是微博这条规则：

```js
RelativeLayout >7 FrameLayout > @[name$="FrameLayout" || name$="ImageView"]
  [clickable=true][childCount<2][width<50&&height<50] <<n [vid="view_recycler" || vid="tweet_list"]
```

被转成了「命中 `view_recycler` 就点」。而 `view_recycler` 是微博信息流的**列表容器**  
（实测 `bounds=[0,240][1080,2269]`，占屏 84.5%）—— 点它的正中心正好落在某条内容上，  
现象就是「开屏跳得挺正常，一进微博就自己乱跳转」。

现在按两条规则定位目标：

1. 有 `@` 就用 `@` 那一段；
2. 没有 `@` 时，注意 GKD 是**自顶向下**搜索的：`A > B` 先找 A 再在 A 的子节点里找 B     
   （目标是 B）；而 `A <<n B` 先找祖先 B、再在 B 的后代里找 A —— **目标是左边那个 A**。     
   所以最右一段若是由 `<` / `<<` 挂上去的，要一路往左退。

目标段里没有 id / text / desc 的（纯结构断言）直接丢弃，**不再拿上下文里的 ID 凑数**。

另外补了两道过滤：

- **容器 ID 黑名单**：以 `recycler` / `list` / `layout` / `container` / `pager` / `grid`    
  等结尾的资源 ID 一律不当点击目标（含 `close` / `btn` / `skip` 等动作词的放行）。
- **泛内容词黑名单**：`推荐`、`广告`、`荐读`、`关注`、`查看详情` 这类词在任何应用里都是    
  内容标签或导航项，GKD 靠 `preKeys` 多步流程才安全，快跳是单步点击，一律不转。

### 把转换结果直接灌进已装好的 App（需 root）

不想手工导入时，可以直接改 App 的 SharedPreferences。快跳的规则分两层，**选错层会很惨**：

| 层       | SharedPreferences 键 | 灌大量规则时的表现                                      |
| ------- | ------------------- | ---------------------------------------------- |
| **订阅层** | `rules_json`        | 界面只显示计数、不逐行渲染 → **首选**                         |
| 本地层     | `local_rules_json`  | 主界面「本地规则」逐行 addView，834 个应用会把界面卡死 → **别灌大规则集** |

文件在 `/data/data/com.laopeng.autoskip/shared_prefs/autoskip_cfg.xml`，工具是 `tools/mkprefs.py`：

```bash
# 1) 先停 App（小米/HyperOS 上 force-stop 会连带清掉无障碍启用状态，之后要补回，见下方）
adb shell am force-stop com.laopeng.autoskip

# 2) 生成注入版 XML —— 自动做 XML 转义，并回读校验内容一致
python tools/mkprefs.py <当前prefs.xml> rules/gkd-compat.json <输出.xml> <毫秒时间戳>

# 3) 推送（Git Bash 会把绝对路径改写掉，用双斜杠抵消）
adb push 输出.xml //data/local/tmp/prefs_new.xml

# 4) 原地写入：用 > 重定向而非 cp —— inode 不变，属主与 SELinux 标签都自动保留
adb shell "su -c '[ -s /data/local/tmp/prefs_new.xml ] && cat /data/local/tmp/prefs_new.xml \
  > /data/data/com.laopeng.autoskip/shared_prefs/autoskip_cfg.xml'"

# 5) 小米/HyperOS 需要把无障碍补回来
adb shell settings put secure enabled_accessibility_services com.laopeng.autoskip/com.laopeng.autoskip.SkipService
adb shell settings put secure accessibility_enabled 1
```

**两个必踩的坑：**

1. **绝不要在 `shared_prefs/` 里留 `autoskip_cfg.xml.bak`。** Android 的 `SharedPreferencesImpl`     
   加载时若发现同目录有 `<文件名>.bak`，会**删掉主文件、把 `.bak` 改名顶替** ——     
   注入的内容会被静默还原成备份的样子。备份要挪到 `/data/local/tmp/` 等其他目录。
2. **写完必须让 App 进程重启**才能读到新配置。若进程还活着，它内存里的旧 prefs     
   会在下一次 `apply()` 时把文件覆盖回去（典型症状：文件大小自己变回去了）。

验证方法：主界面「规则订阅」区块应显示 `当前生效：835 个应用 / 2854 条`  
（835 = 834 个真实应用 + 1 个通配 `*` 组）。

### 从李跳跳规则转换（v1.3.4 新增能力）

李跳跳是另一套体量很大的现成规则库（GitHub 上万星），写法和 GKD 不同，  
转换器是 `tools/ltt2skip.py`：

```bash
python tools/ltt2skip.py
```

**它的规则描述的是「两个控件」，不是一条文案**，这是和 GKD 最大的区别：

```json
{"id": "青少年模式", "action": "我知道了"}
```

`id` 是弹窗的**识别特征**（出现它说明弹窗在），`action` 才是要点的**按钮** ——  
也就是「出现 A 时点击 B」。

而快跳原来的规则只有「匹配到什么就点什么」。直接拿 `action` 去点会出事：  
`action` 里最高频的是 `取消`（38 次）、`我知道了`（37 次）、`关闭`（26 次），满屏都是，  
单独匹配必然误点。

为此 v1.3.4 给规则加了 **`anchor`（前提条件）** 字段：

```json
{
  "name": "李跳跳:打开通知权限 → 再考虑下",
  "matchType": "any",
  "anchor": ["打开通知权限"],
  "matches": ["再考虑下"],
  "action": "click"
}
```

语义是「**anchor 成立，才允许点击 matches 命中的节点**」。`anchor` 为空时行为完全不变，  
已有规则不受任何影响。

几条实现要点：

- `&` = 与、`|` = 或，**AND 优先级高于 OR**（`A&B|C` = (A 且 B) 或 C），与上游写法一致
- 「与项」的判定是「树里存在某个节点包含它」，不是「同一个节点同时包含全部」——    
  上游用 `&` 描述的是「弹窗里同时出现了这几段文字」，同一节点并不一定共存
- anchor 检查放在**找到点击目标之后**才跑：它要扫全树，先跑等于每条规则都白扫一遍
- 转换器丢弃 anchor 短于 2 字符的规则 —— `完成`、`更新` 这种满屏都有，当锚点等于没锚点
- `matchType="any"`（text ‖ desc ‖ id）正好对齐李跳跳的匹配口径

李跳跳规则文件的 key 是包名的 `String.hashCode()`，**不可逆**，得靠包名清单反算；  
而且网上流传的文件常是**多段数组首尾直接拼接**的（段间没有逗号），  
所以转换器用 `raw_decode` 扫描式解析，而不是 `json.loads`。

本轮并入了两份源（上游 `AllRules.json` + 设备侧导出的一份快照），  
产出 **797 条规则 / 328 应用**，与 GKD 产物合并后订阅涨到 **923 应用 / 2938 条**  
（其中 796 条是 `anchor` 式的）。

### 规则加多了怎么防误点：离线回放

规则越多，最大的风险就是**误点**。快跳的诊断模式会把「它自己看到的」节点树落盘，  
`tools/ltt_verify.py` 拿这些 dump，按引擎**同样的判定顺序**（activityIds → matches →  
anchor → 40% 面积闸）重跑一遍：

```bash
python tools/ltt_verify.py <dump目录>
```

正常界面（没弹窗）上**不该有任何规则命中**，命中就是误点。  
本轮用 71 帧真实界面验证，796 条新规则零误触发。

## 八、规则格式

一份规则文件就是一个 JSON（也吃得下带注释、带尾逗号的 json5）。

### 8.1 分组格式（v2，v1.7.0 起的规范格式）

```
订阅 → 应用(RawApp) → 组(RawGroup) → 规则(RawRule)
```

这是照着 **GKD 的层级**做的：一条规则属于某个「组」，组才吃开关。类别的名字直接沿用 GKD 的那套  
**闭集**（`Category.ALL`）—— 开屏广告 / 全屏广告 / 局部广告 / 分段广告 / 更新提示 / 通知提示 /  
评价提示 / 权限提示 / 功能类 / 青少年模式 / 其他。

**为什么是闭集**：上游的组名是长尾的（首页弹窗广告 / 课程广告 / 穿山甲广告…），如果照单全收，  
一百多个一次性组名会散成一堆只有一条规则的组，界面比不分还乱。所以只认这 11 个，  
其余一律落进「其他」。

组名从哪来：GKD 的规则名约定是 `组名-规则名`（如「开屏广告-跳过」），所以  
`Category.of(ruleName)` 取 `-` 之前那段当组名，认不出来就是「其他」。

```json
{
  "version": 2,
  "apps": [
    {
      "id": 1,
      "name": "某应用",
      "packageName": "com.example.app",
      "groups": [
        {
          "key": 0,
          "name": "开屏广告",
          "desc": "",
          "enable": true,
          "rules": [
            {
              "name": "开屏广告-跳过",
              "matchType": "any",
              "matches": ["跳过", "Skip", "跳过广告"],
              "excludes": ["跳过引导", "跳过教程"],
              "activityIds": ["SplashActivity", "AdActivity"],
              "action": "click",
              "maxClick": 2,
              "cooldown": 1500,
              "delay": 0
            }
          ]
        }
      ]
    }
  ]
}
```

`enable:false` 的意思是「作者认为这组不该跑」，**与用户的关停记录取「与」**：  
作者关了就跑不了，用户关了也跑不了，但用户关不掉作者开着的东西以外的语义不受影响。

### 8.2 扁平格式（兼容读入，别再手写）

v1.7.0 之前落盘的就是下面这个扁平形状（`app → rules`）。解析时照旧认，读进来之后  
立刻按规则名前缀补出组名、升成 v2 再存回去：

```json
{
  "version": 1,
  "apps": [
    {
      "id": 1,
      "name": "某应用",
      "packageName": "com.example.app",
      "rules": [
        {
          "name": "跳过开屏广告",
          "matchType": "any",
          "matches": ["跳过", "Skip", "跳过广告"],
          "excludes": ["跳过引导", "跳过教程"],
          "activityIds": ["SplashActivity", "AdActivity"],
          "action": "click",
          "maxClick": 2,
          "cooldown": 1500,
          "delay": 0,
          "enabled": true
        }
      ]
    }
  ]
}
```

`looksLikeGroups()` 靠特征字段分辨两种形状：有 `rules` 就是组，有 `matches`/`match`/`activityIds`  
就是规则本身。这样 `{"apps":[{"packageName":"x","rules":[...]}]}` 这种「组名缺失但套了 rules 壳」  
的中间产物也不会被误判。

> ⚠️ **升级是幂等的，靠 `Prefs.ruleFormat` 而不是靠嗅探内容**。早期版本用>   
> `json.indexOf("\"groups\"")` 判断要不要升级，结果每次启动都要把几百 KB 的 JSON>   
> 重新 parse 一遍。现在存一个 int（0=没归一化过，2=当前格式），跑一次就再也不跑。>   
> 归一化还带**完整性校验**：应用数 / 规则数 / 通配组条数任一变了就整份放弃、原文件不动。

### 应用级字段

| 字段            | 类型     | 说明                               |
| ------------- | ------ | -------------------------------- |
| `packageName` | string | 目标应用包名。填 `*` 表示**对所有应用生效**（通用规则） |
| `name`        | string | 应用名，只用于显示                        |
| `rules`       | array  | 该应用下的规则列表                        |

### 规则级字段

| 字段                   | 类型       | 说明                                                                                                        |
| -------------------- | -------- | --------------------------------------------------------------------------------------------------------- |
| `name`               | string   | 规则名，会出现在跳过记录里                                                                                             |
| `matchType`          | string   | `any`（文字+描述+ID） / `text` / `desc` / `id` / `className`                                                    |
| `matches`            | string[] | 关键词，命中**任意一个**即算匹配                                                                                        |
| `anchor`             | string[] | **前提条件**：界面里必须先出现这些特征，规则才生效；留空 = 无前提。用来承载「出现 A 时点击 B」这类规则（见第七节）。元素之间是「或」，单个元素内部再用 `\|` 分或组、`&` 分与项，AND 优先 |
| `excludes`           | string[] | 反向词，命中则**整条规则作废**（防误触的关键）                                                                                 |
| `regex`              | bool     | `matches` 是否按正则解释，默认 `false`                                                                              |
| `activityIds`        | string[] | 只在界面类名包含这些片段时生效；留空 = 不限                                                                                   |
| `excludeActivityIds` | string[] | 类名包含这些片段时跳过                                                                                               |
| `className`          | string[] | 进一步限定控件类名，例如只认 `TextView`                                                                                 |
| `action`             | string   | 见下表                                                                                                       |
| `delay`              | int      | 命中后延迟多少毫秒再点，默认 `0`                                                                                        |
| `maxClick`           | int      | 单个界面最多点几次，默认 `3`                                                                                          |
| `cooldown`           | int      | 同一条规则两次点击的最小间隔（毫秒），默认 `900`                                                                               |
| `enabled`            | bool     | 是否启用                                                                                                      |

### action 可选值

| 值             | 行为                          |
| ------------- | --------------------------- |
| `click`       | 优先点「可点击的祖先节点」，失败则手势点中心（最常用） |
| `clickSelf`   | 同 `click`                   |
| `clickCenter` | 直接手势点节点中心                   |
| `back`        | 触发系统返回键                     |
| `none`        | 只记录，不操作                     |

## 九、订阅怎么用

1. 把规则 JSON 放到任意能通过 HTTP 访问的地方（GitHub Raw、对象存储、你自己的服务器都行）。
2. App 里粘贴地址 → 「添加订阅」→「更新全部规则」。
3. 拉取成功后规则会缓存到本地，**断网也能继续用**，不受影响。
4. 支持填多个地址，会自动合并；同名包名的规则会叠加。
5. 长按订阅地址可删除。

没填任何订阅时，用的是 `BuiltinRules.java` 里的出厂规则。

### 规则的三层结构（v1.3.2 起）

实际生效的规则 = **出厂兜底 ∪ 本地 ∪ 订阅**，本地排在最前：

| 层    | 来源                  | 更新方式                |
| ---- | ------------------- | ------------------- |
| 出厂兜底 | `BuiltinRules.java` | 随 APK 升级，**永远参与匹配** |
| 本地   | 导入的文件 + 手动添加        | 只增不减，订阅更新不动它        |
| 订阅   | 订阅地址拉取              | 每次更新**整份覆盖**        |

出厂兜底是 v1.3.2 单独拉出来的一层。原先内置规则只在「订阅为空」时才被用到，  
订阅一拉就是几百个应用、整份覆盖，等于把内置规则顶掉了 —— 于是修一个通用缺陷  
（比如「跳过按钮是纯图标、没有文本」）就没法靠升级 APK 下发。单独立一层之后，  
出厂修复在任何配置下都生效，而且因为只有两三条保守的通用规则，不会干扰订阅。

**⚠️ v1.6.0 修掉一个由这层引出的重复问题**：出厂层独立之后，订阅层原先那句  
「订阅为空就回退到内置规则」就成了多余的 —— 它会让内置规则在出厂层和订阅层各出现一次，  
合并后被应用两遍。具体表现是 `*` 通配组从 3 条变成 6 条、几个内置应用各多一条规则。  
现在：

- `remote()` **不再回退**到内置规则。订阅层空就是空，出厂层照常生效。
- 「恢复出厂内置规则」改为**清空订阅层**（而不是把内置 JSON 写进订阅层），    
  效果一样是「只剩内置规则」，但不会重复。

顺带把一个显示口径也纠正了：「规则」页「规则订阅」卡片右边的摘要原先显示的是**三层合并数**，  
让人以为订阅里有九百多个应用 —— 实际那些可能全在本地层。现在它显示订阅层自己的计数，  
点开卡片还能看到「当前生效 / 订阅层 / 本地层」三行明细。

### 出厂层从 v1.3.3 起不只是「通用规则」

除了 `packageName: "*"` 的通用组，出厂层还带**应用专属组**，用来兜住三种订阅覆盖不到的情况：

1. 上游订阅里**根本没有**这个应用；
2. 上游**有规则但把规则组默认关掉了**（GKD 里要用户手动开）；
3. 上游规则是纯结构定位，转换器表达不了。


首批补的是 7 个（详见 `rules/coverage-report.md`）：  
铁路12306、小米钱包、HMS Core、网上国网、有道云笔记、红果免费短剧、转转。

**改出厂规则请改 `tools/builtin_rules.json`，然后跑生成器**——别手改 Java 字符串：

```bash
python tools/gen_builtin.py     # → app/src/main/java/com/laopeng/autoskip/BuiltinRules.java
```

手写那一大坨 JSON 的 Java 转义，漏一个反斜杠就编译不过或规则静默失效，交给生成器更稳。

> **注意**：更新是整份覆盖 —— 每次拉取会重建订阅层。你自己加的东西请放**本地规则**（第九节），>   
> 那是独立的一层，不会被覆盖。

### 写规则的两个实操技巧

- **先看 id 再写文字匹配**。文字匹配最省事，但 App 一改版就失效；控件 ID（`matchType: "id"`）稳定得多。用 Android Studio 的 Layout Inspector，或系统的「开发者选项 → 显示布局边界」配合 `adb shell uiautomator dump` 能拿到界面节点树。
- **`excludes` 一定要留**。比如只写 `matches: ["跳过"]`，可能把「跳过引导」「跳过教程」也点了，用户会以为 App 坏了。规则越通用，`excludes` 越要写全。

## 十、本地规则怎么用

订阅拉下来的规则是**整份覆盖式**更新的 —— 一按「更新全部规则」，上一份就没了。  
本地规则活在另一个抽屉里：**只增不减，订阅怎么更新都不动它**。  
两者叠加生效，本地规则排在前面。

界面上有五个入口：

| 入口               | 适合什么场景                                    |
| ---------------- | ----------------------------------------- |
| **导入规则文件**       | 电脑上写好的 JSON / json5 / txt，传到手机后从文件管理器里挑进来 |
| **粘贴 JSON**      | 从聊天记录、笔记、剪贴板直接粘一段规则进去；有「从剪贴板填入」按钮         |
| **手动添加一条**       | 一个应用只差一个按钮，不想写 JSON，填个表单就行                |
| **把订阅规则转存为本地规则** | 规则库是刷进来/导进来的，想让它在订阅更新时也**不被覆盖**（见 10.1）   |
| **导出本地规则为文件**    | 备份、换机、拿回电脑上编辑（见 10.2）                     |

### 10.1 把订阅规则转存为本地规则

订阅层的特点是**整份覆盖** —— 点一次「更新全部规则」，里面原来是什么就全换成新拉的了。  
如果你手机上的规则集不是从订阅地址拉来的，而是**导入 / 用 root 刷进去**的，  
那它随时可能被一次误操作覆盖掉。转存就是把它挪进本地层：本地层只增不减，  
订阅怎么更新都不动它。

点一下 → 确认 → 转存，界面会告诉你搬了多少：

```
已转存 922 应用 / 2921 条（本地层现有 922 应用 / 2921 条，去重掉 0 条）
```

**为什么要连订阅层一起清空？** 这是这个功能唯一容易踩的地方。三层是**叠加生效**的  
（本地 ∪ 出厂 ∪ 订阅，见第九节），只搬不清的话，同一份规则会在本地层和订阅层各留一份，  
合并后变成双份 —— 引擎是**按条独立执行**的，表现就是同一个按钮连点两下。

所以转存的语义是「**搬家**」而不是「复制」：搬完订阅层清空，**生效规则总数完全不变**。  
设备实测（922 应用 / 2921 条）：

|     | 订阅层             | 本地层             | 当前生效                |
| --- | --------------- | --------------- | ------------------- |
| 转存前 | 922 应用 / 2921 条 | 空               | 924 应用 / **2931 条** |
| 转存后 | 空               | 922 应用 / 2921 条 | 924 应用 / **2931 条** |

逐应用逐条比对：922/922 应用的规则完全一致，换的只是归属层。  
本地层原有的规则会保留、重复的不会叠加（合并时按规则内容去重）；订阅层空着时按钮自动置灰。

### 10.2 导出本地规则为文件

把本地层整个序列化成 JSON 落成一个真文件，用来备份 / 换机 / 拿回电脑上编辑。

- 落盘位置：**`/sdcard/Download/快跳/快跳-本地规则-<时间戳>.json`**
- 弹窗里有「复制路径」和「分享」（走系统分享面板，可直接发到微信 / 网盘）
- Android 10 及以上走 MediaStore 写公共下载目录，**不需要任何存储权限**

> 本工程零第三方依赖，用不了 androidx 的 FileProvider，所以 Android 9 及以下只能落到>   
> 应用私有目录 `/sdcard/Android/data/com.laopeng.autoskip/files/`，且不支持分享，弹窗里会说明。

实测导出 684,916 字符 / 738 KB，标准 JSON 可直接 `json.load` 解析，922 分组 / 2921 条与本地层一致。

> 转存和导出都要解析 / 序列化几百 KB 的 JSON（约 0.5~1 秒），所以两个操作都在>   
> **后台线程**跑，前台只给一个「正在转存…／正在导出…」的进度框 —— 放主线程会卡住界面，>   
> 用户以为没反应就会再点一次。

### 手动添加的表单字段

| 字段       | 说明                                             |
| -------- | ---------------------------------------------- |
| 目标应用包名   | 必填。点「填入当前应用」可自动填入 —— 需要先开着无障碍服务，并**在目标应用里停留过** |
| 规则名      | 可留空，留空时取第一个关键词。日志里显示的就是它                       |
| 匹配方式     | 任意 / 文字 / 描述 / 控件 ID / 类名。**拿不准就选「任意」**        |
| 关键词      | 多个用中英文逗号或换行分隔，例如 `跳过,跳过广告,关闭该广告`               |
| 按正则解释    | 勾上后关键词按正则处理。`^跳过$` 精确匹配、`^跳过` 前缀、`跳过$` 后缀      |
| 动作       | 点击（推荐）/ 点它自己 / 点中心坐标 / 返回键 / 仅记录不点击            |
| 限定界面类名   | 可选。填 `SplashActivity` 之类，只在那个界面生效，能大幅降低误触      |
| 单屏最多点击次数 | 默认 2。同一条规则在同一屏里点够这个次数就停手                       |

### 本地规则的两个开关

- **长按规则条目** → 查看 / 复制 JSON（可用来备份或分享给朋友）或删除该应用的本地规则
- **本地规则独占** —— 打开后，凡是**有本地规则的应用**，它的订阅规则全部让位。    
  什么时候用：某应用的订阅规则和你的本地规则都在点同一个按钮，导致连点两下；    
  或者订阅里那个应用的规则不灵，你想完全自己接管。默认关闭。

### 一条重要提示

本地规则**和订阅规则一样，都是"命中就点"**。写着 `matches: ["关闭"]` 这种宽关键词，  
配上 `packageName: "*"`，就会在每个应用里到处乱点。  
稳妥写法的三条：① 包名尽量写具体；② 关键词越具体越好；③ 能填「限定界面类名」就填上。

## 十一、按应用 / 按规则组开关 & 界面结构

两件事：**想让某个 App 别被快跳管**，以及**规则库里压根没有的 App 也想跳开屏**。

### 11.1 按应用规则开关

底部导航「**应用**」页（v1.5.0 起是独立页，v1.7.0 前是独立 Activity、点主页卡片进去）。

- **搜索框**：按应用名或包名过滤。
- **三个筛选**：`全部` / `有规则` / `已停用`。不想一个个翻的时候，`有规则` 就是快跳当前真正会动手的那批。
- **每条右侧一个开关**：关掉 = **该应用彻底移出快跳的管辖范围** —— 它的订阅规则、出厂规则、本地规则，    
  以及下面要讲的自动识别，一起停。适合那些"它自己弹的东西我宁愿自己点"或者"快跳在这里点错了地方"的场景。
- 列表顶部会实时显示「共 N 个应用 · 已停用 M 个」；列表底部「全部恢复为启用」（需二次确认）一键清空停用名单。

**关停闸门放在哪里，是这件事的关键。** 它写在 `SkipService.scan()` 的**最前面**，早于读节点树：

```java
if (prefs.isAppDisabled(pkg)) return;   // ← 在读 root 之前就返回
```

抓节点树要走一次跨进程调用（`getRootInActiveWindow()`），是整个扫描里最贵的动作。  
如果先抓树再判断，停用就等于白抓 —— 省不了任何开销。

实测验证（A/B 对照）：把 `com.tencent.mm`（**启用**）和 `com.qiyi.video`（**停用**）同时写进诊断名单，  
然后分别冷启动两个 App：

| 应用  | 状态 | 停留界面                 | 产生的诊断 dump 数 |
| --- | -- | -------------------- | ------------ |
| 微信  | 启用 | 正常界面                 | **5**        |
| 爱奇艺 | 停用 | 开屏 `WelcomeActivity` | **0**        |

停用中的爱奇艺明明停在开屏页、节点树唾手可得，却一个 dump 都没产生 —— 证明闸门确实在**读树之前**就短路了。

### 11.2 开屏跳过自动识别（实验性，默认开启）

规则库里没有的应用（实测第三方应用里约 **200/315** 没有专属规则组），可以靠**按钮的形状**去认。  
同一张卡片下半部分的开关「自动识别无规则应用的开屏跳过」控制它。

判定是**四个条件同时成立**才动手，缺一不点：

| 条件       | 判据                                                           | 为什么                        |
| -------- | ------------------------------------------------------------ | -------------------------- |
| **含跳过词** | text / desc / id 里含 `跳过`、`跳過`、`略过`、`skip`                    | 词是主证据，优先级 text → desc → id |
| **小**    | 占屏面积 ≤ **12%**                                               | 跳过按钮一定是小控件；整屏容器不是          |
| **在角上**  | 右上（`cy < 30%高` 且 `cx > 55%宽`）或 右下（`cy > 72%高` 且 `cx > 55%宽`） | 开屏跳过按钮只有这两个位置              |
| **短**    | text / desc ≤ **12** 字（**控件 ID 不计长度**）                       | 排除"跳过本次更新去体验新版本吧"这类长句      |

另外还要求节点**可见**、**尺寸非零**、自身或近祖先**可点击**。

**故意不认的东西**（这些比"漏跳"危险得多）：

- `关闭` / `取消` / `我知道了` —— 开屏页上也常见，但点错会关掉正常页面或误触业务弹窗。    
  这类词交给规则库精确定位，绝不参与自动识别，也绝不自动转换。
- **裸倒计时数字**（`3`、`5s`）—— 没有上下文，它可能只是页码、评分、数量。宁可漏，不可错。

**准入限制**（即使四条件全中也要过这些闸）：

- **只在无专属规则组时启用** —— `RuleStore.hasAppRules(pkg)` 为假。有规则的走规则，避免两套逻辑打架。
- **只在冷启动后 6.5 秒内** —— `withinAutoWindow()`。
- **不止看时间，还看界面** —— 只有当前 Activity 是该应用的**启动 Activity**（`PackageManager` 里查得到的 launcher intent），    
  或距切到前台不到 3.5 秒，才算"开屏"。进到主界面之后就不再自动动手。
- **不在桌面** —— `isHomePkg()` 排除启动器。
- **次数上限** —— 每个前台会话最多 **2** 次，同一屏最多 **1** 次。

命中后走的点击路径和规则命中**完全一样** —— 复用 `RuleEngine.clickNode()`，  
包含 40% 面积兜底、向上找可点击祖先、`performAction` 失败退回手势点中心这一整套安全闸。  
日志里会记成 `自动识别 <包名> · 开屏跳过 · 「<命中文字>」`，一眼能和规则命中区分开。

**实测结果**：挑 8 个无专属规则的应用冷启动，诊断输出全部是  
`hit=false` / `fg_ms≈280–400`（在窗口内）/ `launchAct=true`（启动 Activity 识别正确）/ `autoUsed=0`，  
判词为`无命中（含跳过词 0 个：面积挡 0 / 位置挡 0 / 不可点挡 0）`。  
把这批真机节点树做**离线全量扫描**，含 `跳过/跳過/skip/略过` 的节点数为 **0**，  
在 40 个真实帧上**零命中、零误点**。

> 这就是"实验性"的含义：它只在这个样本上被证明**不误点**，还没被证明在足够多的应用上**跳得掉**。>   
> 发现它点错了，就把这个总开关关掉，或在应用列表里单独停掉那一个 App。

### 11.3 怎么排查它为什么没动

诊断模式（见第十二节）现在会额外落一份 `*_auto_*.txt`，内容是：

```
hit=false
cls=...WelcomeActivity
fg_ms=312              ← 距切到前台多少毫秒（>6500 就不在窗口内）
launchAct=true         ← 是否被认作启动 Activity
autoUsed=0             ← 本会话已自动点了几次
无命中（含跳过词 0 个：面积挡 0 / 位置挡 0 / 不可点挡 0）
```

最后那行是**分档淘汰统计** —— 直接告诉你卡在哪一步：  
`含跳过词 0 个` 说明压根没找到带跳过词的节点（多半是纯图标按钮，去加 ID 规则）；  
`面积挡 N` 说明词找到了但块太大（可能是容器）；`位置挡 N` 说明位置不在右上/右下；`不可点挡 N` 说明没有可点的祖先。

> **诊断限流**：`fg_ms` 每帧都在变，早期版本会因此**每帧写一个文件**（一次冷启动 100+ 个）。>   
> 现在加了 `autoNoteFresh` —— 每个前台会话最多记 **1** 条"无命中"，命中则必记。实测降到 **1–4 文件/应用**。

### 11.4 按规则组开关（v1.7.0）

比 11.1 的「按应用开关」细一档：用户想说的常常是「这个应用的开屏广告别管，但更新提示还是要跳」，  
一刀切把整个应用摘出去太粗。

**两级粒度，两条键**：

| 在哪里关                 | 写的键     | 影响面     |
| -------------------- | ------- | ------- |
| 「应用」页 → 点进某个应用 → 组开关 | `包名#组名` | 只有这一个应用 |
| 「规则」页 → 全局规则卡        | `*#组名`  | 所有应用    |

`RuleStore.rulesFor(pkg)` 里两者取「或」：`包名#组名` 命中、**或** `*#组名` 命中，这一组就跳过。

**关键设计：过滤发生在「选规则」这一层，不在匹配那一层。** `rulesFor()` 直接把被关停的组  
的规则从返回列表里剔掉，引擎根本看不见它们 —— 比「匹配上之后再看一眼要不要点」省一整个  
扫描轮次，也不存在漏判。

> **口径坑（踩过）**：应用节点和 `*` 节点在 `addRules()` 里都用**真实包名**过滤，所以>   
> `包名#组名` 能连带压住同名的**全局**组。实测淘宝总规则 24 条（自己 19 + 全局 5），>   
> 关掉「开屏广告」后剩 21 条 —— 少的正是它自己的 1 条 + 全局的 2 条。>   
> 「对所有应用都关」那是 `*#组名` 的语义，别混。

**实测（v1.7.0，淘宝 / 淘票票 / 阿里云盘）**：三个应用在「列表行条数」、  
「详情页摘要」、「诊断模式里的 `ruleCount`」三处显示同一个数：

| 应用   | 规则分布（离线基线）                         | 列表行 / 详情页 / 引擎 |
| ---- | ---------------------------------- | -------------- |
| 淘宝   | 自己 19 + 全局 5                       | 24 / 24 / 24   |
| 阿里云盘 | 全屏 1 + 局部 1 + 功能 3 + 其他 7 + 全局开屏 2 | 14 / 14 / 14   |
| 淘票票  | 开屏 3（含全局 2）+ 其他 3（出厂）              | 6 / 6 / 6      |

组关停的实测（**预测值 → 实测值全部吻合**）：

| 写入的键                          | 预期削掉的规则          | 结果              |
| ----------------------------- | ---------------- | --------------- |
| 无（基线）                         | —                | `ruleCount=6`   |
| `*#其他`                        | 出厂层 `*`/其他 3 条   | `ruleCount=3` ✓ |
| `*#开屏广告`                      | 自己 1 + 全局 2      | `ruleCount=3` ✓ |
| `com.taobao.movie.android#其他` | 只为淘票票削掉全局「其他」3 条 | `ruleCount=3` ✓ |

> **组名会随规则更新而变**（上游把「开屏广告」并进「全屏广告」之类），对不上的旧键自然失效、>   
> 不会误伤别的组 —— 代价是那条设置会被静默忽略，所以「规则」页的全局卡会显示>   
> 「已关停 N 组」、底部导航的「规则」标签也会带角标，让用户看得见。

### 11.5 界面结构：底部导航四页（v1.7.0）

原先把八块内容全堆在一页上（改动前 892 行 XML），首屏要滚八屏才看得全。现在拆成四页：

| 页  | 内容                                   |
| -- | ------------------------------------ |
| 首页 | 状态总览 / 排查引导 / 运行设置 / 跳过统计 / 最近跳过记录   |
| 应用 | 搜索 + 筛选（全部·有规则·已停用）+ 逐应用开关 + 进详情看规则组 |
| 规则 | 全局规则 / 规则订阅 / 本地规则                   |
| 设置 | 开屏跳过自动识别 / 后台保活 / root 增强            |

**实现方式：`<include>` + `visibility`，不用 Fragment / ViewPager2。**  
本工程是**零第三方依赖**的（不吃 androidx），所以没有 `FragmentActivity`、没有 `ViewPager2`。  
四页一起 inflate 进 `FrameLayout`，切页只改 `setVisibility`。

副作用（其实是好处）：四页各自保留滚动位置，从「规则」页翻到一半切去「应用」再回来不会被打回顶部；  
四页的折叠卡状态也互不影响。

> ⚠️ **被 include 的页面里所有 id 在同一个 Activity 里必须唯一**（四页同时存在），>   
> 加新控件时注意别撞。`tools/split_pages.py` 按注释锚点切分时已经保证过一遍。

**四个页面的取舍**：

- **「应用」页故意不套 `ScrollView`** —— 列表要自己滚，套两层会打架。
- **「应用」页不在启动时建列表**：遍历全部已安装应用取名字和图标（实测 299 个）要一两秒，    
  而另外三页根本用不到。所以推迟到用户第一次真点进「应用」页才建（`AppsPage.refresh()`），    
  代价是初次进来能瞥见一瞬间的「正在读取应用列表…」。
- **底部标签带角标**：有东西被关停时，「应用」/「规则」标签会显示 `应用 3` 这样的数字并染成警示色。    
  拆成四页之后，用户关掉的东西最容易"看不见" —— 站在首页上完全感觉不到应用页里停用了几个。
- **返回键先回首页，在首页才退出**：四页共用一个 Activity，直接 `finish()` 的话用户在「设置」页    
  按返回会整个 App 退掉，和他在首页按返回没区别，不符合直觉。
- **应用详情仍是独立 Activity**（`AppRuleActivity`）：详情属于"钻进去看"，用返回键退回来比留个 tab 更自然。

**应用详情页把两块分开画**：「专属规则」是这个应用自己的组，「全局规则（这些组对所有应用生效，  
这里只在本应用里关）」是只活在 `*` 节点里、这个应用没有专属组的那些组。  
分开的理由是关掉一个全局组的影响面比关掉一个专属组大得多，得让用户看得见自己在关什么。

**每行组的小标签**只说"为什么它现在不是你想的样子"：

| 标签    | 含义                     | 开关能否点           |
| ----- | ---------------------- | --------------- |
| 已关停   | 用户在这个应用里关过             | 能               |
| 已全局关停 | 被 `*#组名` 关了            | 否（置灰，要去「规则」页恢复） |
| 上游停用  | 规则文件里写了 `enable:false` | 否（置灰）           |
| 全局    | 这一组在全局规则里也有            | 能               |

置灰而不是藏起来 —— 让用户看得见"这里有一组规则，但不是在这一层管的"。

## 十二、常见问题

**Q：无障碍开关是灰色的，点它提示「受限制的设置 / 未知来源应用」？**  
Android 13+ 对侧载应用的默认限制，见第四节「开关是灰色的、点不动」。关键动作只有一个：  
进应用详情页 → 右上角 ⋮ →「允许受限制的设置」。找不到就上 ADB。

**Q：装了没反应？**  
先看 App 顶部是否显示绿色「已开启」。再看「最近跳过记录」有没有条目：

- 完全没记录 → 无障碍服务没起来，或被系统杀了（去做第五节的后台白名单）
- 有记录但没跳掉 → 命中了但点不动，改用 `action: "clickCenter"`，或在规则里加 `delay` 试试

**Q：界面底部显示的版本号是什么？为什么它跟刚装的版本对不上？**  
那是页脚的自报版本。**v1.3.5 之前版本号被写死在 `strings.xml` 的 `footer` 里**，  
发版时忘了改这一行，界面就一直显示旧版本号（实际装的是新包）—— 1.3.2 / 1.3.3 / 1.3.4 三期都中招。  
v1.3.5 起改成启动时从已安装包读取 `versionName`，与系统「应用信息」里显示的版本必然一致。  
要核实真身，以命令行输出为准：

```bash
adb shell "dumpsys package com.laopeng.autoskip | grep -E 'versionName|versionCode'"
```

**Q：为什么以前打开 App 看不到顶部的状态卡？**  
MIUI / HyperOS 把系统默认主题的标题栏渲染成「盖在内容之上」的一层（实测占屏幕顶部约 276px），  
而页面内容是从 y=0 开始排的 —— 于是第一张卡片（服务状态卡）被标题栏整块压住，看着就像「什么都没有」。  
这是从最早版本就存在的老问题，v1.4.0 起换成无标题栏主题、由布局自绘标题，一并解决了。

**Q：每个区块右边的小三角是干什么的？**  
那是折叠开关。v1.4.0 起把「后台保活 / root 增强 / 规则订阅 / 本地规则 / 最近跳过记录」收成了  
可折叠卡片，标题栏右侧常驻一行**实时摘要**（例如「保活正常 ✓」「924 应用 · 2931 条」「200 条」），  
不展开就能判断是否正常。点标题栏任意位置即可展开 / 收起。  
「最近跳过记录」默认只列最近 8 条，需要看全时点下方「展开全部 N 条」。

**Q：会不会乱点？**  
不会超出规则。没命中的按钮一律不碰。但规则写得越宽（尤其 `packageName: "*"`），误触概率越高，所以内置通用规则刻意收得很紧。


**Q：点了「启用 root 增强」，只闪一句「没拿到 root 权限」，开关又弹回去了？**  
KernelSU 的授权窗被国产 ROM 拦掉了（澎湃 / ColorOS / OriginOS 都会）。按第六节手动授权一次：  
KernelSU 管理器 → 超级用户 → 找到「快跳」→ 设为允许 ROOT。之后就能直接用。

**Q：某个 App 开屏跳得挺好，但一进主界面 / 详情页就自己乱跳转？**  
先看 App 里的「最近跳过记录」，按 detail 分两种：

- **detail 是容器 ID**（`xxx_recycler`、`xxx_list`、`xxx_container`）——规则把「定位用的容器」    
  当成了点击目标。典型是微博：`分段广告-信息流广告` 命中了 `com.sina.weibo:id/view_recycler`    
  （信息流列表，占屏 84.5%），点它的正中心正好落在某条内容上。这类规则要从规则集里剔掉，    
  v1.2.4 起转换器已修复（只从 `@` / 方向推断出的目标段取关键词），并加了 40% 面积兜底。
- **detail 是泛词**（`推荐`、`广告`、`关注`、`详情`）——关键词太宽，撞上了内容标签或导航项。    
  给这条规则补 `activityIds` 限定，或者直接删掉重录一条更精确的。

判据一句话：**日志里 detail 是控件 ID 或小按钮文字才正常；是容器 ID / 泛词就该处理。**

**Q：无障碍开关、或者「启用自动跳过」开关，刚打开就自己关了？**  
v1.2.3 之前有两个原因，都已在 v1.2.3 修掉：

**原因一：快跳把自己点关了（最常见）。** 快跳界面上的「启用自动跳过」里带着「跳过」两个字，  
而通用规则的匹配词也是「跳过」。切应用的过渡瞬间，无障碍事件来自 A 应用、活动窗口却还停在快跳，  
于是快跳拿着 A 的规则去扫自己的界面，把自己的设置开关当成广告按钮点了。  
判断方法：旧版「最近跳过记录」里会出现  
`跳过 com.android.settings · 开屏广告-全局 · 「启用自动跳过」` 这种条目——  
只要看到 detail 是「启用自动跳过」，就是它。实测最容易触发的场景是**下拉通知栏**，  
以及在系统设置 / 文件管理器里配置完快跳再切回来。  
v1.2.3 起：扫描前校验 `事件包名 == getRootInActiveWindow().getPackageName()`，跳过快跳自身，  
点击前再用当前活动窗口复核一次 + 确认节点仍可见。

**原因二：服务进程崩溃，系统随即自动关闭无障碍总开关。**  
根因是节点树遍历原先用递归，而部分 ROM（尤其 MIUI）的无障碍缓存偶发会返回**成环**的节点树，  
递归直接把 main 线程 8MB 的栈打爆（`StackOverflowError`）。  
它是 `Error` 不是 `Exception`，外层的 `catch (Exception)` 兜不住，进程当场崩，  
系统就把无障碍开关关了。v1.2.3 起改成**显式栈遍历**（根本不会栈溢出），  
并叠加深度上限 40 层、`AccessibilityNodeInfo` 访问去重、单次扫描节点上限 3000，  
所有 `catch` 一律提到 `Throwable`。顺带把每条正则都做了编译缓存  
（原先每次匹配都 `Pattern.compile`，几千条规则会把主线程拖死）。

如果升到 v1.2.3 后仍偶发被关，才轮到 ROM 自己的策略（部分 ROM 限制侧载应用的无障碍），  
用系统设置里的「无障碍快捷方式」做成悬浮球一键切换即可。

**Q：某个 App 的开屏广告跳不过，日志里一条记录都没有？**

先怀疑「**跳过按钮没有文字**」。典型是阿里系的开屏广告（「美数」SDK，节点 ID 前缀 `ms_`）：  
跳过按钮是一个**纯图标 `View`** —— `text` 和 `content-desc` 都是 `null`，  
只匹配文本的规则永远命中不了它。快跳在菜鸟裹裹上实测到的原始节点是：

```
android.view.View | id=com.cainiao.wireless:id/ms_skipView | t=null | d=null | click=false | vis=true | 948,108 94x94
```

按钮明明可见、位置也对，就是没文本。v1.3.2 起在出厂规则里补了按资源 ID 的匹配  
（`/ms_skipView$`、`/ms_skipView_container$`），菜鸟裹裹以及其他用同款 SDK 的 App 就都能跳了。  
你遇到别的 App 出现同样症状时，按下面的诊断模式抓一次树，把它的跳过按钮 ID 加进本地规则即可。

**Q：怎么看清「快跳到底看到了什么」？**

v1.3.2 内置了诊断模式，不用重编译。以 root 往 App 私有目录写一个 `diag.txt`，  
里面是**要诊断的包名**（一行一个或空格分隔）：

```sh
D=/data/user/0/com.laopeng.autoskip/files
U=$(stat -c %u /data/user/0/com.laopeng.autoskip)
mkdir -p $D && chown $U:$U $D && chmod 771 $D
printf 'com.example.app\n' > $D/diag.txt && chmod 644 $D/diag.txt
restorecon -RF $D      # SELinux 标签不对的话 App 读不到
```

然后照常打开目标 App（冷启动才有开屏广告），界面树会落在 `$D/diag/<包名>_<时间戳>.txt`：

```
pkg=com.example.app
cls=...Activity
ruleCount=14
hitCount=0          ← 0 表示这一屏没有任何规则命中
---- nodes ----      ← 每个带文本/描述/资源ID的节点一行
类名 | t=文本 | d=描述 | id=资源ID | click=可点 | vis=可见 | big=是否大块区域 | 坐标 尺寸
```

排查完记得删掉 `$D/diag.txt` 关掉诊断。

**为什么不用 `uiautomator dump` 抓？** 它是 UiAutomation，会要求**独占无障碍连接**，  
一执行就把快跳的服务顶下线重连 —— 抓到的树是它自己的，不是快跳看到的，  
而且会顺带把快跳的「跳过」时机打乱。诊断模式导的是快跳自己的 root 节点，才是真实视角。

---

**Q：某个 App 我不想让快跳管，怎么办？**  
「应用」页 → 搜到它 → 关掉右边那个开关即可。  
关掉后该应用的**规则和自动识别一起停**，并且是在读节点树之前就返回，不产生任何开销。  
列表顶部显示「共 N 个应用 · 已停用 M 个」，底部有「全部恢复为启用」。详见第十一节。

**Q：只想让某个 App 的「更新提示」照常跳，但别管它的开屏广告？**  
这是要按**规则组**关，不是整个应用。「应用」页 → 点这一行（不是点开关）→ 进详情页 →  
在「专属规则」或「全局规则」块里关掉「开屏广告」那一组。详见第十一节 11.4。

**Q：关掉某个规则组之后，感觉它还在跑？**  
先分清你关的是哪一级：「应用」详情页里的开关只对**这一个应用**生效（写 `包名#组名`），  
「规则」页的全局卡是**对所有应用**生效（写 `*#组名`）。两者取「或」，所以想彻底停掉某组的两级都得关。  
例外是：如果这一组在某应用里有**专属**规则，那在应用详情页关掉这一组会**连带**压住同名的全局组  
（因为过滤用的是真实包名），不必再去全局卡关一遍。

另外注意，**被关停的组在条数统计里仍然算数**：详情页摘要和「应用」页列表显示的是  
「这一组有多少条规则」，不是「现在跑几条」。想知道真正跑了几条，看诊断模式里的 `ruleCount`。

**Q：列表里的「N 条规则」和点进去详情页的条数一样吗？**  
一样，而且是刻意对齐的（v1.7.0 修过一个不一致：列表只算应用自己的组、详情页把全局组的贡献也算进来了，  
同一个应用会显示 19 / 24 两个数）。现在两边都用「按组名归并三层 × （本应用节点 + 全局节点）」的口径，  
含全局贡献。所以列表写「24 条规则（含全局）」、点进去也是「N 组 · 24 条规则」。

**Q：自动识别（无规则应用的开屏跳过）会不会点错东西？**  
它只在**四个条件同时成立**时才动手：含跳过词 + 面积 ≤12% + 在右上或右下角 + 文字不超过 12 字。  
`关闭`/`取消` 这类危险词**明确不认**，裸倒计时数字（`3`、`5s`）也不认。  
另外它只在冷启动后 6.5 秒内、且停在启动 Activity 时才启用，每会话最多 2 次、每屏最多 1 次。  
实测 8 个无规则应用冷启动 + 40 个真实界面的离线回放，**零命中、零误点**。  
不喜欢可以整个关掉（同一张卡片里的开关），或者只停掉个别应用。详见第十一节 11.2。

**Q：自动识别明明该跳却不动，怎么知道卡在哪一步？**  
开诊断模式，看 `*_auto_*.txt` 最后那行分档统计，例如  
`无命中（含跳过词 0 个：面积挡 0 / 位置挡 0 / 不可点挡 0）`：  
`含跳过词 0 个` = 按钮没有文字（多半是纯图标，去加 ID 规则）；  
`面积挡 N` = 词找到了但块太大；`位置挡 N` = 不在右上/右下；`不可点挡 N` = 找不到可点祖先。  
同时核对 `fg_ms`（>6500 就出了时间窗）和 `launchAct`（应为 true）。

**Q：我的规则集是用 root 刷进去的，怕点错被覆盖掉，怎么办？**  
本地规则区有「把订阅规则转存为本地规则」—— 一键把订阅层整体搬进本地层。  
本地层只增不减，订阅怎么更新都不动它。  
注意它是**搬家不是复制**：搬完订阅层会清空（否则同一份规则会在两层各留一份、被应用两遍，  
表现是同一个按钮连点两下），生效规则总数不变。详见 10.1。

**Q：导出的规则文件在哪？怎么发给别人？**  
`/sdcard/Download/快跳/快跳-本地规则-<时间戳>.json`。导出后的弹窗里有「分享」，  
走系统分享面板可以直接发微信 / 网盘；也有「复制路径」。详见 10.2。

**Q：能像 GKD 那样用社区订阅吗？**  
能，工程内带了转换器 `tools/gkd2skip.py`，把 GKD 订阅（json5）转成快跳格式，  
详见第六节。注意转换是**有损**的：GKD 有约八成规则靠 `clickable`、`childCount`、  
节点索引这类属性断言定位，快跳的引擎里没有对应概念，只能丢弃。  
另外订阅里没有、只想加一两条的情况，直接用第九节的「手动添加」更快。

**Q：订阅更新后，我自己加的规则还在吗？**  
在。本地规则是独立的一层，订阅更新只覆盖订阅层。  
「恢复出厂内置规则」也只重置订阅层，不会动你的本地规则。
